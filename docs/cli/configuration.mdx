The CLI uses YAML configuration files to manage system connections. You can configure multiple IBM i systems, set a default, and switch between them with the `--system` flag.

---

## Config File Locations

The CLI loads configuration from two locations. Project-level config overrides user-level config:

| Scope | Path | Use Case |
|-------|------|----------|
| **Project** | Nearest `.ibmi/config.yaml` walking up from `cwd` | Team-shared settings, project-specific systems |
| **User** | `~/.ibmi/config.yaml` | Personal systems, global defaults |

The CLI walks up the directory tree from your current working directory to find the nearest `.ibmi/config.yaml` — similar to how `.gitignore` files work.

---

## Config File Format

```yaml
# Default system to use when --system is not specified
default: dev

# Default output format (optional)
# Overrides TTY auto-detection when set
format: table    # table | json | csv | markdown

# Named system connections
systems:
  dev:
    host: dev400.example.com
    port: 8076
    user: DEVUSER
    password: ${DB2i_PASS}
    readOnly: false
    confirm: false
    timeout: 60
    maxRows: 5000
    ignoreUnauthorized: true

  prod:
    host: prod400.example.com
    port: 8076
    user: ${PROD_USER}
    password: ${PROD_PASS}
    readOnly: true
    confirm: true
```

### System Properties

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `host` | string | *required* | IBM i hostname or IP address |
| `port` | number | `8076` | Mapepire port |
| `user` | string | *required* | IBM i user profile |
| `password` | string | — | Password or `${ENV_VAR}` reference |
| `description` | string | — | Human-readable label |
| `defaultSchema` | string | — | Default schema for unqualified table names |
| `readOnly` | boolean | `false` | Restrict to SELECT statements |
| `confirm` | boolean | `false` | Prompt for confirmation before `ibmi sql` and `ibmi tool` execute. `ibmi sql --yes` skips the prompt. Without a terminal, a single-system command runs without asking; a multi-system `ibmi sql` requires `--yes` |
| `timeout` | number | `60` | Query timeout in seconds |
| `maxRows` | number | `5000` | Default row limit for queries |
| `ignoreUnauthorized` | boolean | `false` | When `true`, accept any TLS certificate without verifying it (test systems only). The default verifies it |
| `tools` | string[] | — | Default YAML tool path(s) for this system |
| `sshKey` | string | — | Connect over SSH with this private key. See [SSH Connections](#ssh-connections) |
| `sshHostKeySha256` | string | — | Expected SSH host key fingerprint |
| `sshTechnique` | `tcp` \| `cli` | `tcp` | JDBC technique over SSH |
| `keepSession` | boolean | `true` | Keep an SSH session open between commands |

## Environment Variable Expansion

Use `${VAR_NAME}` syntax in config values to reference environment variables. These are expanded at load time:

```yaml
systems:
  dev:
    host: ${DB2i_HOST}
    user: ${DB2i_USER}
    password: ${DB2i_PASS}
```

This lets you keep credentials in your shell environment or `.env` file rather than in the config file itself.

## System Resolution Order

When a command needs a system connection, the CLI resolves it in this priority order:

<Steps>
  <Step title="--system flag">
    Explicit flag always wins.

    ```bash
    ibmi sql "SELECT 1 FROM SYSIBM.SYSDUMMY1" --system prod
    ```
  </Step>

  <Step title="IBMI_SYSTEM environment variable">
    Set in your shell or `.env` file.

    ```bash
    export IBMI_SYSTEM=prod
    ibmi schemas
    ```
  </Step>

  <Step title="Config default">
    The `default:` key in your config file.

    ```yaml
    default: dev
    ```
  </Step>

  <Step title="Implicit single system">
    If only one system is configured, it's used automatically.
  </Step>

  <Step title="Legacy DB2i_* environment variables">
    Falls back to `DB2i_HOST`, `DB2i_USER`, `DB2i_PASS`, and `DB2i_PORT` from the environment. This provides zero-config compatibility with existing MCP server setups.
  </Step>
</Steps>

## Password Resolution

When a system connection requires authentication (a system with `sshKey` needs no password):

1. **Config `password` field** — including `${ENV_VAR}` expansion
2. **Interactive prompt** — if running in a TTY, prompts for password with hidden input
3. **Error** — if non-interactive (piped) and no password is available

<Warning>
Password values are never logged, displayed in `--watch` headers, or included in error output.
</Warning>

## SSH Connections

A system can connect over SSH instead of the Mapepire daemon. The CLI then starts `mapepire-server` on the IBM i through SSH, so no Mapepire daemon or port `8076` is needed. A system uses SSH when it has an SSH key:

```bash
ibmi system add dev --host dev.example.com --user MYUSER \
  --ssh-key ~/.ssh/id_ed25519 \
  --ssh-host-key-sha256 SHA256:AbC...
```

```yaml
systems:
  dev:
    host: dev.example.com
    user: MYUSER
    sshKey: ~/.ssh/id_ed25519
    sshHostKeySha256: SHA256:AbC...   # recommended
```

| Property | Default | Description |
|----------|---------|-------------|
| `sshKey` | — | Path to a private key, absolute or starting with `~/`. The system then connects over SSH |
| `sshHostKeySha256` | — | Expected host key fingerprint (`SHA256:<base64>` from `ssh-keygen -lf`, or 64 hex chars). Without it the host key is **not** verified |
| `sshTechnique` | `tcp` | JDBC technique on the IBM i: `tcp` (JTOpen, a `QZDASOINIT` job) or `cli` (the native driver, often faster) |
| `keepSession` | `true` | Keep an SSH session open between commands (see below) |

- SSH uses key authentication only. The CLI never asks for a password for an SSH system, and never sends one over SSH.
- Key setup, supported key formats and host key verification are the same as for the MCP server: see [SSH Transport](/configuration#ssh-transport).
- `DB2i_SSH_PASSPHRASE` (encrypted keys) and `DB2i_SSH_PORT` (default `22`) are read from the environment.
- With the [legacy `DB2i_*` fallback](#system-resolution-order), `DB2i_SSH_KEY` and `DB2i_SSH_HOST_KEY_SHA256` select SSH in the same way.

### SSH sessions

An SSH connection takes a few seconds to open (SSH, a Java start and the database connection). So that only the first command pays for it, the CLI keeps an SSH **session** open for each system:

- The first command on the system opens the session. It starts a small background process, the session host, that holds the SSH connection and one SQL job.
- Later commands send their SQL to the session host. They take well under a second.
- A session closes after 10 minutes with no command (`IBMI_SESSION_IDLE_SECONDS` changes this), when a statement times out, or with `ibmi system disconnect`.
- Changed connection settings, or a new CLI version, open a new session. The old one closes when it is idle.

```bash
ibmi system status            # the transport and session of each system
ibmi system disconnect dev    # close the session of dev
ibmi system disconnect --all  # close all sessions
ibmi sql "VALUES 1" --fresh   # connect for this command only
```

<Warning>
All commands on one system share one SQL job while the session is open. What one command sets stays for the next one: `SET SCHEMA`, temporary tables in `SESSION`, uncommitted changes. Run `ibmi system disconnect <name>` or use `--fresh` for a clean job. Set `keepSession: false` (or `system add --no-keep-session`) to open a new connection for every command.
</Warning>

The session host listens on a socket in `~/.ibmi/run/` that only your OS user can open (directory `0700`, socket `0600`). It gets the system's host, user and key path, never a password. Its log, in the same directory, records when it starts and stops and any connection error, never SQL.

Not covered by sessions: systems with a password (Mapepire daemon), and `ibmi sql --system a,b` runs on several systems, which open their own connections. `ibmi system test` always opens a new connection.

## Managing Systems

Use `ibmi system` subcommands to manage connections:

```bash
# Add a new system (interactive password prompt)
ibmi system add staging --host staging400.example.com --user STGUSER

# Add a system that verifies the server's TLS certificate
ibmi system add prod --host prod400.example.com --user PRODUSER --verify-tls

# List all configured systems
ibmi system list

# Show details for a system
ibmi system show dev

# Set the default system
ibmi system default prod

# Add a system that connects over SSH
ibmi system add dev --host dev400.example.com --user DEVUSER --ssh-key ~/.ssh/id_ed25519

# Show the transport and SSH session of each system
ibmi system status

# Close the SSH session of a system
ibmi system disconnect dev

# Test connectivity
ibmi system test dev
ibmi system test --all

# Remove a system
ibmi system remove staging

# Show config file locations
ibmi system config-path
```

## Output Format Priority

When determining the output format, the CLI checks in this order:

1. `--raw` flag (equivalent to `--format json`)
2. `--format <type>` flag
3. `format:` in config file
4. Auto-detect: `table` for TTY, `json` for piped output

Set a default in your config to always get consistent output:

```yaml
format: table   # always render tables, even when piped
```
